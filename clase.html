2. Anatomía de una clase (ClassDef)

CampoTipoObligatorioNotas
idstringSíIdentificador único (p. ej. "barbarian"). Se referencia desde otros objetos.
displayDisplayInfoSíBloque de presentación. Solo name es obligatorio.
hitDieintSíDado de golpe (6, 8, 10, 12).
primaryAbility[string]NoCaracterísticas primarias (p. ej. ["STR"]).
recommendedAbilityOrder[string]NoOrden de prioridad para el array estándar (15,14,13,12,10,8). Vacío = STR..CHA.
savingThrows[string]NoSalvaciones con competencia (p. ej. ["STR","CON"]).
proficienciesClassProficienciesNoCompetencias de armadura/armas/habilidades.
startingEquipment[EquipmentItem]NoEquipo inicial. Cada ítem lleva display y, opcionalmente, id del objeto del catálogo (ver §2.1).
goldAlternativeint?NoOro alternativo al equipo inicial.
subclassUnlockLevelint?NoNivel al que se elige subclase (p. ej. 3).
progression[LevelRow]NoTabla nivel a nivel (1–20).
features[FeatureDef]NoRasgos de la clase.
subclasses[SubclassDef]NoSubclases disponibles.

DisplayInfo

Presente en clases, rasgos, subclases y opciones. name es lo único obligatorio.

{
  "name": "Bárbaro",
  "description": "Texto largo opcional.",
  "icon": "🔥",
  "flavorText": "Cita ambiental opcional."
}

ClassProficiencies

{
  "armor":  ["light", "medium", "shields"],
  "weapon": ["simple", "martial"],
  "skills": ["Atletismo", "Percepción"],
  "tools":  [],
  "numSkillChoices": 2
}

numSkillChoices = cuántas habilidades elige el jugador de la lista skills.

startingEquipment

Cada ítem tiene un display (nombre) y, opcionalmente, un id que lo enlaza a un objeto del catálogo (EquipmentDef). Cuando el id está presente, el motor mete ese objeto directo en el inventario del personaje al crearlo (enlace fiable). Sin id, intenta resolver el objeto por nombre (heurístico; puede fallar si el nombre no casa). Recomendado: usar id.

"startingEquipment": [
  { "display": { "name": "Espada larga" }, "id": "longsword" },
  { "display": { "name": "Paquete de explorador" }, "id": "explorers_pack" },
  { "display": { "name": "15 po" } }
]
El oro suelto ("15 po") va sin id: el motor lo detecta por el patrón "N po" y lo suma al oro inicial en vez de meterlo como objeto.

3. La tabla de progresión (progression)

Es una lista de filas (LevelRow), una por nivel:

{ "level": 1, "proficiencyBonus": 2, "features": ["rage","unarmored_defense"], "table": { "rage_uses": 2, "rage_damage": 2 } }
CampoTipoNotas
levelintNivel de clase (1–20).
proficiencyBonusint?Bono de competencia en ese nivel.
features[string]IDs de rasgos que se desbloquean en ese nivel. Deben coincidir con features[].id.
tablemap<string,int>Mapa libre clave→entero.

table es la clave de las mecánicas que escalan. Un RESOURCE (u otros grants) con scaling.rule = "FROM_TABLE" y tableKey = "rage_uses" lee el valor de table["rage_uses"] en el nivel actual. Así defines "cuántas furias por nivel" sin escribir código.

Los features de la fila de progresión enlazan por id con el features de la clase. El texto del rasgo vive una sola vez en features; la tabla solo lo referencia.

4. Rasgos (FeatureDef)

Un rasgo es una unidad de contenido con presentación (display) y cero o más mecánicas (mechanics).

{
  "id": "rage",
  "level": 1,
  "display": { "name": "Furia", "description": "…", "icon": "🔥" },
  "mechanics": [ /* grants */ ]
}
  • id (obligatorio): único dentro de la clase; es lo que referencia progression.
  • level (opcional): nivel al que aparece.
  • display (obligatorio).
  • mechanics (opcional): lista de grants. Puede ir vacía → el rasgo es solo texto.

Un rasgo puramente narrativo:

{
  "id": "danger_sense",
  "level": 2,
  "display": { "name": "Sentir el peligro", "description": "Ventaja en TS de Destreza…", "icon": "👁️" },
  "mechanics": []
}

6. Subclases (SubclassDef)

Una subclase reutiliza el mismo FeatureDef que la clase. Sus rasgos suelen llevar el level correspondiente, y si un grant debe aplicar solo a esa subclase, se marca con subclassId.

{
  "id": "berserker",
  "display": { "name": "Senda del Berserker", "flavorText": "…", "description": "…" },
  "features": [
    {
      "id": "berserker_intimidating_presence",
      "level": 14,
      "display": { "name": "Presencia intimidante", "description": "…", "icon": "😈" },
      "mechanics": [
        {
          "type": "RESOURCE",
          "id": "intimidating_presence_use",
          "label": "Presencia intimidante",
          "recovery": "LONG_REST",
          "scaling": { "rule": "FIXED", "value": 1 },
          "minLevel": 14,
          "subclassId": "berserker"
        }
      ]
    }
  ]
}

En la clase, la elección de subclase se modela con un CHOICE de kind: "SUBCLASS" en el rasgo del nivel indicado por subclassUnlockLevel.

6.1 Subclase lanzadora 1/3 (Caballero Arcano / Embaucador Arcano)

Una subclase puede convertir a su clase (no lanzadora de base) en lanzadora parcial. Es el caso del Caballero Arcano (Guerrero) y el Embaucador Arcano (Pícaro): lanzan 1/3 de la progresión. Se declara poniendo un SPELLCASTING con casterType: "THIRD" dentro de una feature de la subclase, marcado con subclassId para que solo aplique a quien la elija.

{
  "id": "eldritch_knight",
  "display": { "name": "Caballero Arcano", "description": "…" },
  "features": [
    {
      "id": "eldritch_knight_lanzamiento_de_conjuros",
      "level": 3,
      "display": { "name": "Lanzamiento de conjuros", "description": "…" },
      "mechanics": [
        {
          "type": "SPELLCASTING",
          "casterType": "THIRD",
          "ability": "INT",
          "spellListClassId": "wizard",
          "subclassId": "eldritch_knight"
        }
      ]
    }
  ]
}

Valores de casterType y cómo cuentan para el nivel de lanzador (incluido el multiclase):

casterTypeClasesAporta al nivel de lanzador combinado
FULLBardo, Clérigo, Druida, Hechicero, Magonivel completo
HALFExplorador, Paladínla mitad (↑ si es tu única clase lanzadora; ↓ al multiclasear)
THIRDCaballero Arcano, Embaucador Arcanoun tercio (redondeo hacia abajo)
WARLOCKBrujono cuenta aquí: usa su propia tabla de Pacto

Notas de la implementación actual (fase 1):

  • El motor ya suma el THIRD al nivel de lanzador combinado y calcula espacios y CD de salvación correctamente a partir del ability indicado.
  • Los límites por tabla de subclase (cuántos trucos/conjuros preparados concretos permite la subclase a cada nivel) y la restricción de escuela del PHB (Caballero Arcano: Abjuración/Evocación; Embaucador Arcano: Encantamiento/Ilusión) aún no se modelan: el jugador aprende de la lista de spellListClassId sin ese filtro. Son refinamientos futuros.

7. Cómo encajan las piezas (flujo mental)

  1. Defines la clase con su display, hitDie, competencias y equipo.
  2. Rellenas progression nivel a nivel: en cada fila listas los ids de los rasgos que se desbloquean y los valores de table que escalan.
  3. Defines esos rasgos en features, cada uno con su display y sus mechanics.
  4. Las mecánicas que crecen con el nivel leen de table vía scaling.rule = "FROM_TABLE".
  5. Añades subclasses, cada una con sus propios rasgos y grants marcados con subclassId.

Regla de oro: el texto vive una vez (en features / subclasses[].features); la tabla de progresión solo referencia por id.

9. Checklist antes de dar por buena una clase

  • [ ] id, display.name y hitDie presentes.
  • [ ] Todo id en progression[].features existe en features[].id.
  • [ ] Cada costResource apunta a un RESOURCE.id que existe.
  • [ ] Cada scaling.tableKey (FROM_TABLE) tiene su clave en table de cada nivel relevante.
  • [ ] Los grants de subclase que deban aislarse llevan subclassId.
  • [ ] Los type de grant coinciden con el catálogo (§5); un typo se degrada a UNKNOWN.
  • [ ] Valida el JSON: importarlo como pack usa ContentPackSerializer.parseOrNull, que devuelve Result en vez de lanzar.
Referencia viva: compara siempre con barbarian_example.json, que ejercita casi todos los grants (RESOURCE, COMBAT_TOGGLE, COMBAT_ACTION, CHOICE, AC_FORMULA, DAMAGE_RESISTANCE, DAMAGE_BONUS, EXTRA_ATTACK, SPEED_BONUS, ABILITY_BOOST y subclases con subclassId).

Otros tipos de contenido

Todos los objetos de un pack comparten dos bloques ya vistos en la clase:

  • display (DisplayInfo): name obligatorio; description, icon, flavorText opcionales.
  • mechanics / grants (lista de *grants*): las mismas mecánicas del catálogo de §5. Un grant con type desconocido degrada a UNKNOWN sin romper el parseo.

Cada tipo vive en su lista dentro del ContentPack: species, backgrounds, feats, spells, invocations, equipment, beasts.
