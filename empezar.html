Primeros pasos

Esta guía explica cómo definir el contenido de la app en el formato JSON que deserializa: clases (y subclases), trasfondos, especies, dotes, conjuros, invocaciones, equipo y bestias. Todo el contenido es *data-driven*: no hay lógica hardcodeada. Cada objeto vive en un content pack y el motor lo interpreta a partir de sus mecánicas (mechanics / grants, llamadas *grants*).

La guía arranca por la clase (el objeto más grande y completo, §1–§9) y luego cubre el resto de tipos (§10–§17), las unidades de distancia (§18), cómo importar (§19) y ejemplos completos listos para copiar de cada tipo (§20).

Modelo de referencia en código: shared/src/commonMain/kotlin/com/dnd/shared/content/ (ClassDef.kt, FeatureDef.kt, Grant.kt, LevelRow.kt, Scaling.kt, BackgroundDef.kt, SpeciesDef.kt, FeatDef.kt, SpellDef.kt, InvocationDef.kt, EquipmentDef.kt, BeastDef.kt, etc.)

Ejemplo real completo de una clase en el repo: .kiro/specs/modelo-data-driven/barbarian_example.json

Punto de partida recomendado: plantilla-pack.json es un pack mínimo y válido con un objeto de cada tipo (clase con subclase, especie, trasfondo, dote, conjuro, invocación, equipo y bestia), incluidos los grants que más suelen fallar (AC_FORMULA, SPEED_BONUS, EXTRA_ATTACK). Cópiala, cambia los ids (conviene usar un prefijo propio para no pisar objetos del SRD) y borra lo que no uses. Antes de importar, pásala por Validar un pack sin importarlo en Gestión de contenido.

1. Dónde vive una clase: el content pack

Una clase nunca va suelta. Va dentro de un ContentPack, en la lista classes:

{
  "version": "2",
  "id": "mi_pack",
  "name": "Mi pack de clases",
  "author": "Tu nombre",
  "license": "…",

  "classes": [ /* aquí van una o más clases (ClassDef) */ ],
  "species": [],
  "backgrounds": [],
  "feats": [],
  "spells": [],
  "invocations": [],
  "equipment": [],
  "beasts": []
}

Solo id es obligatorio en el pack; todas las listas son opcionales (un pack puede aportar solo clases).

Reglas de parseo que conviene conocer

El deserializador (ContentPackSerializer) está configurado así:

  • Discriminador "type": dentro de mechanics, el campo type decide qué grant es.
  • ignoreUnknownKeys = true: campos extra en el JSON no rompen el parseo.
  • Degradación elegante: un type de grant que el motor no conoce se convierte en UNKNOWN en vez de fallar. El display del rasgo se sigue mostrando.
  • explicitNulls = false: puedes omitir los campos opcionales en lugar de ponerlos a null.

19. Importar contenido en la app: pack completo vs. objeto individual

La app ofrece dos formas distintas de importar un JSON, y cada una espera una forma de JSON diferente. Este es un error común: un mismo archivo puede funcionar por una vía y fallar por la otra.

19.1 Importar como PACK (Gestión de contenido → Importar pack)

Espera un ContentPack completo: el objeto raíz con id (obligatorio) y las listas (classes, species, backgrounds, feats, equipment, …). Es el formato que describe toda esta guía (§1). Un pack puede traer varios objetos y de varios tipos a la vez (p. ej. una especie más su arma en equipment), y todos entran juntos.

{
  "version": "2",
  "id": "senda_dhampir_test",
  "name": "Dhampir 5.5 — Pack de prueba",
  "species": [ { "id": "dhampir_55", "display": { "name": "Dhampir" }, "speed": 35, "...": "..." } ],
  "equipment": [ { "id": "dhampir_vampiric_bite_weapon", "...": "..." } ]
}
Si tu contenido tiene más de un objeto o mezcla tipos (una especie + un arma, una clase + sus conjuros, etc.), importa como pack. Es la única vía que trae todo junto.

Validar antes de importar. El botón Validar un pack sin importarlo (Gestión de contenido) lee el JSON y muestra todos los errores y avisos con su ruta, sin instalar nada. Si un import falla, la app muestra ese mismo informe.

Dónde se guarda y cómo recuperarlo. Al importar, la app guarda su propia copia del pack (Android: filesDir/packs/<id>.json; iOS: Documents/packs/<id>.json). Borrar el archivo original no afecta al pack instalado. Se identifica por el id del pack: importar otro con el mismo id lo reemplaza (la app conserva un respaldo .bak del anterior). Para recuperar un pack instalado, usa Exportar pack en su tarjeta de Gestión de contenido.

19.2 Importar un OBJETO INDIVIDUAL (Importar especie / dote / clase / trasfondo)

Cada botón de importación individual espera el objeto suelto, es decir, un único elemento del tipo correspondiente sin el envoltorio del pack. Al importar una especie, el JSON raíz debe ser un SpeciesDef, no un ContentPack.

Correcto para "Importar especie" (el objeto que iría *dentro* de species: [ … ]):

{
  "id": "dhampir_55",
  "display": {
    "name": "Dhampir",
    "description": "Un linaje tocado por una naturaleza vampírica…",
    "icon": "🩸",
    "flavorText": "Entre la vida y la muerte, el hambre permanece."
  },
  "creatureType": "HUMANOID",
  "speed": 10.5,
  "size": "MEDIUM",
  "darkvision": 18,
  "traits": [ /* … los mismos traits … */ ],
  "mechanics": []
}

Incorrecto para "Importar especie" (esto es un pack, da error): un objeto raíz con version, id de pack y listas classes / species / equipment. Ese formato solo lo acepta "Importar pack".

Campos que la app usa para reconocer cada tipo individual (deben estar presentes en la raíz):

Import individualCampos que debe tener el objeto raíz
Especieid, display, speed
Claseid, display, hitDie, savingThrows
Doteid, display, category
Trasfondoid, display, goldAlternative, startingEquipment

19.3 Regla práctica y limitación

  • Un solo objeto de un solo tipo → puedes usar el import individual (objeto suelto) o un pack. Ambos sirven.
  • Varios objetos o varios tipos (p. ej. especie + arma) → usa pack. El import individual solo trae ese objeto: cualquier equipo, conjuro u otro objeto asociado que viva en otra lista del pack no se importa por la vía individual.

Ejemplo concreto: el Dhampir de prueba define su "Mordisco Vampírico" como arma en equipment. Si lo importas como especie individual, la especie entra pero el arma no. Para que entren ambos, impórtalo como pack.
